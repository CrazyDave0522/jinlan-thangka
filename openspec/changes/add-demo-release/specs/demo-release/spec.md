## ADDED Requirements

### Requirement: Staged demo acceptance

The release process SHALL distinguish milestone A, an empty-archive preview with engineering and deployed-flow acceptance, from milestone B, real-data/domain acceptance. It SHALL retain requirements 1–7 and SHALL NOT mark the whole change complete while B is deferred or not run.

#### Scenario: Continue while real material is unavailable

- **WHEN** the archive is empty and curated material remains deferred
- **THEN** engineering, actual empty-archive/model and Vercel Preview checks can proceed without importing records or configuring curated reference assets
- **AND** actual retrieval/citation support and specific-work accuracy remain explicitly unevaluated.

#### Scenario: Report milestone A completion

- **WHEN** A's required local, actual deployed and hands-on checks pass
- **THEN** the report identifies revision/deployment, settings, evidence types and limitations
- **AND** B and whole-change completion remain open.

### Requirement: Integrated deterministic verification

Release verification SHALL exercise text/image conversation, retrieval outcomes, answers, source inspection/copying and relevant failures through isolated test infrastructure. It SHALL reuse feature coverage, add meaningful tests for uncovered integration and keep synthetic data/grants outside ordinary deployments and the real archive.

#### Scenario: Verify composed interactions and failures

- **WHEN** the real Next.js route uses isolated synthetic provider/archive upstreams
- **THEN** submission, selected-image analysis, follow-up, reread and source/copy interactions preserve accepted associations, context and independent drafts
- **AND** timeout, invalid-output, unavailable/reference/gateway failures publish no partial success and preserve accepted correction/retry behavior.

#### Scenario: Verify the ordinary release build

- **WHEN** release checks follow the isolated browser suite
- **THEN** a separate ordinary production build succeeds with fixture aliasing disabled and the ordinary empty reference manifest
- **AND** synthetic evidence is not served as product data or represented as actual provider/domain acceptance.

### Requirement: Honest empty-archive operation

The system SHALL support enabled text/image conversations against a successfully readable empty archive without inventing records, sources, specific artwork identities or inspection of unselected historical pixels. It SHALL distinguish completed empty retrieval, no retrieval and retrieval failure, preserving uncertainty and archive/general knowledge boundaries.

#### Scenario: Complete a supplied-name lookup with no results

- **WHEN** the configured archive returns no matches for a supplied artist/artwork name
- **THEN** the reply presents the completed-empty outcome and appropriately qualified general content
- **AND** it exposes no fabricated evidence, reference comparison or source title.

#### Scenario: Explain selected pictures and follow up

- **WHEN** selected pictures and later summary questions are processed without archive evidence
- **THEN** observations belong to their own pictures, tentative/unreadable details remain qualified and unselected history is not presented as freshly inspected
- **AND** a detail unavailable in prior observations/history offers explicit reread for unambiguous unselected targets, with the captured question/pictures, a counted new attempt and preserved newer draft.

### Requirement: Verified Vercel preview configuration

The release SHALL verify the existing Vercel project, deployment revision, Preview scopes, server-only provider configuration, ordinary build, transport budgets and effective function duration. It SHALL preserve existing production mapping during Preview acceptance and use no database initialization, remote fixture seeding or visitor Storage resources.

#### Scenario: Begin with no configured service variables

- **WHEN** the deployed candidate has no Supabase or provider settings configured
- **THEN** its page remains available and valid text/selected-image submissions produce the defined unavailable outcomes without provider access or fabricated archive results
- **AND** archive/provider acceptance stays not run until initial scoped setup and a new deployment are verified; local environment files are not treated as deployed configuration evidence.

#### Scenario: Verify a disabled preview

- **WHEN** generation and vision are disabled on the target deployment
- **THEN** the Chinese empty interface and safe unavailable/error outcomes can pass without provider calls
- **AND** this does not pass successful generation or image-understanding acceptance.

#### Scenario: Verify an active preview

- **WHEN** deployed access/window and funded scope are agreed and both capabilities are enabled
- **THEN** agreed text/image cases exercise actual provider and empty-archive services through the deployed app
- **AND** statuses, usage, latency, failures and uncertainty are recorded rather than inferred from local configuration.

#### Scenario: Verify access and request boundaries independently

- **WHEN** scoped archive reads and malformed non-paid request probes are performed
- **THEN** HTTP/column access, expected empty rows and complete metadata/permission checks are distinguished
- **AND** application reads/probes use no elevated database credentials or provider calls; separate read-only administrative inspection does not introduce a stronger application key.

#### Scenario: Confirm the intended archive is actually empty

- **WHEN** A06 is verified for the actual Preview's Supabase project/configuration
- **THEN** scoped anon table/RPC reads are paired with fresh read-only owner/admin counts for all eight business tables and inspected grants/RLS/policies in that same project
- **AND** an empty anon result, local configuration for another project or unavailable administrative inspection does not pass authoritative emptiness/access acceptance.

#### Scenario: Probe byte admission with malformed JSON

- **WHEN** ASCII bodies of `{` followed by spaces use application/json at exactly 4,000,000 and 4,000,001 UTF-8 bytes
- **THEN** the application returns 400/invalid_request and 413/request_too_large respectively, both as JSON with Cache-Control: no-store and without provider calls
- **AND** a gateway-handled response is recorded separately and does not substitute for the expected application outcome.

### Requirement: Bounded evaluation

Actual-provider evaluation SHALL use fixed inputs, sessions and expectations within the agreed funding/access scope. A batch SHALL allow at most six dispatched submissions/twelve provider calls, count failures/timeouts/cancellations and reread, and stop on failure, unmet prerequisite or cap without retries or replacements. Existing authorization SHALL retain its original scope.

#### Scenario: Review actual empty-archive outputs

- **WHEN** the agreed batch runs
- **THEN** each output/failure is reviewed for relevance, picture association, uncertainty and fabricated archive/source claims
- **AND** stopped dependent cases are recorded as not run, with dispatches, observed stages/usage, unknown activity, latency and available measured expenditure recorded without credentials or visitor payloads.

#### Scenario: Completion or billing evidence is incomplete

- **WHEN** a dispatched attempt fails, is aborted or lacks a completion event or provider billing result
- **THEN** the report distinguishes dispatches, observed stages/usage and unknown activity or pending expenditure
- **AND** missing logs never mean zero calls/cost or restore allowance; up to two calls per dispatched attempt remain conservatively reserved until reliable evidence resolves the count.

#### Scenario: Missing-detail smoke prerequisite is unavailable

- **WHEN** the fixed P05 target detail is already represented in the observations/history available to the model
- **THEN** P05 and its dependent P06 are recorded as not run because the required missing-detail condition was not established
- **AND** the reviewer does not fail an otherwise appropriate summary answer or spend extra submissions to force clarification.

#### Scenario: Budget the owner's active device review

- **WHEN** desktop/mobile hands-on review includes live model submissions
- **THEN** those actions are scheduled within the six-submission batch or available separately agreed scope before dispatch
- **AND** later checklist placement does not grant extra calls; remaining repeated controls/source checks use isolated fixtures or disabled Preview and missing participation stays open.

### Requirement: Recoverable deployment

Test deployments SHALL end with both model switches false unless ongoing enabled scope is explicitly agreed. The release SHALL verify rollback and direct test-URL retirement/control without unbudgeted provider calls, preserving pre-existing production settings/mapping and archive data. Per-runtime admission SHALL NOT be presented as a global spending cap.

#### Scenario: End or roll back the enabled test

- **WHEN** the test window ends or acceptance fails
- **THEN** the reviewed prior working deployment or disabled baseline is restored as agreed
- **AND** enabled test deployments/direct URLs are retired or controlled and final capability state is verified without data changes or blind policy resets.

### Requirement: Responsive and hands-on integrated review

The demo SHALL preserve readable content, reachable controls, proportional pictures, independent scrolling and draft/focus behavior across the existing eight core viewports and affected intermediate, landscape and reduced-height states. Review SHALL distinguish automation/emulation from hands-on/native-device results.

#### Scenario: Review integrated layout and interaction

- **WHEN** the ordered text/four-picture/summary/clarification/reread/draft/copy/reload journey runs through isolated real-route upstreams at each of the eight core viewports, alongside dedicated long-answer/source/failure and affected resize checks
- **THEN** no page horizontal overflow, clipped primary content or inaccessible/overlapping composer controls occurs
- **AND** representative visual evidence and unavailable native keyboard/selection checks are recorded without claiming measured audience coverage.

#### Scenario: Review sources while the live archive is empty

- **WHEN** the owner reviews source actions before real sources exist
- **THEN** rich evidence uses an identified isolated fixture environment while actual empty replies remain free of fabricated sources
- **AND** source/copy behavior passes do not establish actual citation-quality acceptance.

### Requirement: Deferred real-data and final acceptance

Full release acceptance SHALL retain actual retrieval, claim-to-source support, numbered/ordinary-unnumbered identification positives, similar/ambiguous negatives and actual reference permission/access checks. Missing material or domain judgments SHALL stay deferred/not run. Whole completion SHALL require both milestones, final integrated owner acceptance and the agreed verified Vercel deployment.

#### Scenario: Resume real-data acceptance

- **WHEN** actual records/sources, permitted assets/grants, expected domain judgments and funded scope become available
- **THEN** retained cases verify actual UUIDs, scoped support and real reference access/bytes under the archived image acceptance protocol
- **AND** synthetic positives and empty-archive results do not substitute for them.

#### Scenario: Reject unsupported whole-release acceptance

- **WHEN** a result has false definite identity, invented sources, unsupported archive claims or unevaluated required real-data cases
- **THEN** affected acceptance remains failed, not run or deferred as appropriate
- **AND** other engineering or Preview passes do not establish whole-release completion.

#### Scenario: The final candidate differs from earlier milestone evidence

- **WHEN** code, deployment settings, archive data or reference grants change after an accepted milestone
- **THEN** final review identifies the candidate's commit/deployment/configuration/data/grant state, reruns affected checks within their agreed scope and records a rationale for reused unchanged evidence
- **AND** historical empty-archive acceptance does not accept the new artifact or require deleting later curated data; empty-state regressions remain isolated while final live checks use current data.
