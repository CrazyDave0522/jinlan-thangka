## Counts and Byte Budgets

| Boundary | Revised policy | Rationale |
| --- | --- | --- |

| Retained prepared attachments per page | At most 20 distinct attachment identities | Allows five full four-picture sets or twenty single-picture turns without unbounded thumbnail/history growth. This is an engineering starting value, not measured audience behavior. |

Twenty includes selected drafts, successful turns, failed/unavailable previews and blobs retained by retries/snapshots, counting each shared identity once. Referencing an existing picture again does not consume another retained slot; selecting/preparing the same file as a new attachment does. Release attachments only when no page state references them. Reject a new batch atomically if it would exceed the retained limit, preserving the old state and explaining deliberate refresh/full-clear. Do not evict history automatically. Client page accounting enforces retained count; the server independently bounds the request manifest and actual inputs and cannot measure other tabs or local unsent files.

Preserve 5,000,000 original bytes, 16,000,000 original pixels, 8192 original side, 500,000 prepared bytes, 1600 prepared longest side, 4,000,000 complete incoming UTF-8 bytes and the 32,000,000 retained-prepared-byte guard. The count limit usually binds before the old retained-byte limit. Decoded/transient memory is separate. Preserve 32 messages, 2,000 current-text and 16,000 combined context/observation text code points. Count summaries against context limits rather than create an unbounded side channel.

The four active/twenty retained limits apply to visitor attachments. They count distinct identities, not provider exposures; a selected visitor picture may be sent again only in targeted verification. Up to four authorized archive references have a separate transient server budget and do not consume visitor attachment slots. No reference-image bytes are inserted into the visitor composer or retained conversation. Bounded stable image/artwork IDs and comparison provenance may be retained as result metadata; they neither count as visitor attachments nor grant later byte access.

More than four active visitor inputs is a corrective preflight error: ask to reduce new/selected pictures while preserving the composer. The twenty-picture limit uses deliberate full-clear refresh. A request byte overflow remains independently enforced; unused historical bytes no longer consume that request budget.

Historical pictures may be selected while a new batch is being prepared. Recheck the combined active count immediately before committing that batch. If the total exceeds four, reject the entire new batch, release its prepared previews and preserve historical selections and text; the valid two-new/two-history boundary remains usable. ## Specific Archive-Work Identification

The response must distinguish identified, candidates, no_match and insufficient_evidence per requested image group, with real artwork UUIDs and server-owned evidence. Title/deity/style resemblance, a single returned candidate, user assertion or record review status alone cannot establish image-to-record identity. Identification does not certify authenticity.

The readable-identifier path uses a clearly readable collection identity plus accession number observed in the selected picture(s), an exact structured archive query resolving that pair to one uncapped root, fresh supporting collection/accession fields with matching field-scoped sources, and no unresolved identity conflict or disputed supporting evidence. Both identifiers must be supported, not invented from the retrieved candidate. A partial/uncertain reading, matching title alone, duplicate pair, capped result or conflicting evidence remains candidates/insufficient_evidence. If the first-stage visual reading and archive values disagree, do not silently correct the image reading from the record.

The server can validate string/record/source/provenance agreement, not prove OCR or semantic correctness. Positive/negative real cases and domain review are required before accepting this path as accurate. An ordinary unnumbered work must also have an identification acceptance path: retrieve candidates from visible subject/composition/inscription clues, then compare the selected visitor image against authorized reference images and source-supported distinctive record features in the second call. Similarity alone remains candidate evidence. A definite association requires documented correspondence of distinctive features and provenance to one real work without unresolved plausible alternatives. A cropped/altered view or uncertain detail cannot be declared identified merely because it resembles the first candidate.

The exact positive/negative evidence matrices are fixed in [identification](identification.md): current selected pixels, verified artwork/reference rows, field-scoped source support, two qualifying distinctive match features, and actual negative coverage of every competing candidate. Shared-field proof keys deduplicate; generic style/deity/title resemblance is insufficient. Model confidence alone is never a gate. Real acceptance must include (a) a numbered/labelled positive case, (b) an ordinary unnumbered positive image whose archive work exists, and (c) a visually similar different-work negative case. Failure to support case (b) is a missing required capability, not a candidate-only release success. No vector service is assumed; choose further candidate-retrieval changes only when representative samples demonstrate a need. Gate types and public associations are fixed in [contracts](contracts.md); [acceptance](acceptance.md) defines hard failures and positive/negative cases.
